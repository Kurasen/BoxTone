# 为什么 Windows 版能写 5.7 秒，鸿蒙版只能写 2.5 秒

> 对象：华为 FreeClip 2（固件自报型号 `BTFT0027`），协议 2（`0x09` 命令族）
> 依据：Windows 版 `OpenFreebuds-portable` 的运行日志、多轮鸿蒙真机日志（2026-11-18）

---

## 结论（TL;DR）

同一副耳机、同一套 MBB 协议、同一套 969 字节分包，**写入时长的差距全部来自「数据经蓝牙串口从手机到耳机的这一段」**：

| | Windows 版 | 鸿蒙版 |
|:--|--:|--:|
| 串口有效速率 | **~100 KB/s** | **~20 KB/s（慢 4~5 倍）** |
| 擦写闪存（数据落盘） | ~50 KB/s | ~50 KB/s（**完全一样**） |

擦写段两边一致，说明**慢的不是耳机，是传输**。而耳机还有一个约 9.2 秒的会话预算，Windows 的传输足够快、能挤进去，鸿蒙传输太慢、挤不进去，所以长音效在鸿蒙上写不进。

---

## 一、实测数据

### 1.1 同一个「8 帧分片组」的耗时

耳机按 7680 字节（8 帧 × 960）为一个窗口，收到一组才回一次进度。对比两边完成一组的时间：

```
Windows  openfreebuds.log
  144166  0903（耳机：给我下一组）
  144243  0905（耳机：收到 7680）        →  77ms  ≈ 100 KB/s

鸿蒙  boxtone-*.log
  43.544  09 03
  44.052  09 05                              →  508ms ≈ 15 KB/s
  （多轮实测 ackLag 在 280~510ms 之间波动，随耳机状态变化）
```

鸿蒙这边无论怎么改写入方式——逐帧写、整窗 7792 字节一次写（`BULK_WRITE ms=1`）——窗口总时长都不变。说明瓶颈不在应用代码，在协议栈/链路的排包节奏。

### 1.2 擦写段完全一致

耳机把收到的数据落盘（写闪存）时，进度按 4096 字节一跳：

```
Windows：~82ms / 4096 字节 ≈ 50 KB/s
鸿蒙   ：~82ms / 4096 字节 ≈ 50 KB/s
```

两边一模一样。所以「耳机本身写不快」这个假设不成立。

### 1.3 总时长对照（以 5.7 秒 = 192000 字节为例）

| 阶段 | Windows | 鸿蒙 |
|:--|--:|--:|
| 建链 | ≈0（会话常驻） | 2~5s（要先断音频再连） |
| 传输数据 | 3.75s | ~8~10s |
| 擦写闪存 | 4.5s | 4.5s |
| 最终确认 | ~3s | 从不补 09 06，空等 |
| **合计** | **~12s → 成功** | **>13s → 擦写中途耳机重启** |

## 二、根因：差在「传输」这一段，三个层面

### 2.1 传输通道不同

**Windows（OpenFreebuds）**用的是 Linux/Unix 系蓝牙 socket：

```python
sock = socket.socket(AF_BLUETOOTH, SOCK_STREAM, BTPROTO_RFCOMM)
sock.connect((address, 1))     # 直连 RFCOMM 通道 1，不走 SDP
sock.sendall(...)              # 塞进内核缓冲，驱动连续排包
```

8 次 `sendall` 只是把数据丢进内核缓冲，真正的发送由驱动背靠背排完，空口几乎不空闲。

**鸿蒙**走的是 `@ohos.bluetooth.socket`：

```ts
socket.sppConnect(address, { uuid, secure, type })  // 走 SDP，没有 channel/port 参数
socket.sppWriteAsync(id, buffer)                     // 一次写 7792 字节也只返回 1ms
```

`BULK_WRITE ms=1` 证明数据已经进了协议栈缓冲，但之后协议栈按 ~480 字节的 PDU 节奏、逐包等流控放行，实测稳定在 ~20 KB/s。这个节奏不受写入方式影响，是协议栈的排包策略决定的。

### 2.2 链路模式不同（音频通道）

- **Windows**：全程 A2DP 在线，ACL 一直处于高吞吐的 active 模式。
- **鸿蒙**：耳机不允许「音频 + 串口」共存——实测 A2DP 一进入连接态，SPP 随即回 2901054（`AUDIO_KEEP_FAILED`）。所以必须先断开 A2DP 才能连串口；断掉后 ACL 没有音频流，控制器把它放进低功耗（sniff）模式，串口吞吐掉到 ~20 KB/s。

这一层是「能连上但慢」的直接原因：不是我们不想保持音频，是耳机不让。

### 2.3 API 能力受限，无法照搬 Windows

- 鸿蒙 SPP 没有 `channel` / `port` 参数，无法跳过 SDP 直连 RFCOMM 通道 1。
- 无法设置 RFCOMM 的 MTU / 流控 credit 窗口，吞吐完全由协议栈决定。
- 理论上唯一等价的路是 `SPP_L2CAP + psm` 自己实现 RFCOMM 帧（SABM/UA 建链、UIH 带地址、FCS 校验）——成本和风险远大于收益，且要赌系统允许对端未声明 PSM 的连接。

## 三、耳机侧还有一个硬约束：~9.2 秒会话预算

把同一天所有「写满 100%」和「写到一半停掉」的时刻对齐后，规律非常清晰：

| 包长 | 结果 | 从 09 01 算起的完成/中断时刻 |
|--:|:--|--:|
| 106968（3.2s） | 100% | 9132ms |
| 116988（3.5s） | 100% | 9132ms |
| 120328（3.6s） | 100%（仅一次） | 9209ms |
| 120328 | 停在 99.4% | ~9100ms 后耳机收掉会话 |
| 133688（4.0s） | 停在 85% | ~9100ms 同上 |

三次成功全卡在 9.13~9.21 秒，失败全在 ~9.1 秒被耳机自己收掉（随后 200ms 内系统把 A2DP 连回来）。**9.2 秒是耳机给的会话预算，不是我们设的。**

- Windows 数据段只要 3.75s + 擦写 4.5s = 8.9s，正好挤进去。
- 鸿蒙数据段要 8~10s，加上擦写怎么都装不下。

于是「3.2 秒稳、3.6 秒看运气、4 秒以上必挂」——这不是"包太长被截断"，而是毫秒级的预算边缘，传输慢的那一方必然先出局。

---

## 四、结论与当前策略

1. **不是"包太长"，是"链路太慢"。** FreeClip 2 的擦写缺陷（长包随机重启）+ 鸿蒙 SPP 慢 4~5 倍，二者叠加把稳定上限压到 ~2.5 秒。
2. 应用层能做的优化（整窗合并写、去掉帧间空档、收包轮询提速）都已做完，剩余的瓶颈在协议栈，改不动。
3. **当前策略：统一 2.5 秒上限、不区分机型，以稳定优先；** 失败时如实报错并给出可执行指引，不再卡 60 秒。
