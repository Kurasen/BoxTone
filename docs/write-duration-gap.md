# SPP 写入时长：最终实测结论（2026-11-19）

> 对象：华为 FreeClip 2（固件 `BTFT0027`），协议 2（`0x09` 命令族）
> 依据：2026-11-18 ~ 19 的多轮真机日志 + Windows 版 OpenFreebuds 逆行
> 本文取代之前所有关于「9.2 秒会话预算」「盲发可提速」的结论

---

## 结论（TL;DR）

**鸿蒙版能稳定写入的上限是 2.5 秒（83500 字节），3.2 秒（106968 字节）压线，4 秒以上必挂。**
5.7 秒不是代码问题，是两条硬约束叠加：

| 约束 | 数值 | 能否改 |
|:--|:--|:--|
| 系统 SPP 分段 | 480 字节 / 20ms ≈ **23KB/s** | 应用层无接口 |
| 耳机擦写 | 单次 >106KB 时第二阶段会卡死 | 耳机侧问题 |

数据段可以完整传完（4.5s、5.7s 都验证过），**卡住的是耳机的校验擦写阶段**。

---

## 一、关键实测数据

### 1.1 灌水测速：本地快，空口慢

```
写入 192000 字节，用时 281ms，平均 683KB/s   ← 只是写进协议栈缓冲
耳机随后确认：+112/+445/+761/…/+2786ms → 69120
```

耳机的确认是线性的，**每窗（7680B）稳定 330ms**：

| 时刻 | offset | 间隔 |
|--:|--:|--:|
| +112ms | 7680 | — |
| +445ms | 15360 | 333ms |
| +761ms | 23040 | 316ms |
| +1113ms | 30720 | 352ms |
| +1444ms | 38400 | 331ms |
| +1792ms | 46080 | 348ms |
| +2131ms | 53760 | 339ms |
| +2467ms | 61440 | 336ms |
| +2786ms | 69120 | 319ms |

**7680B ÷ 330ms ≈ 23KB/s**，与停等模式完全一致。写入本地再快也改变不了这个节奏。

### 1.2 停等写入：每窗耗时与包长无关

5.7 秒（190468 字节）停等实测：

```
22:19:07.121  09 01
22:19:15.491  offset=176640      ← 8.37 秒
每窗 ackLag 270~386ms（平均 ~300ms）
22:19:46.401  flushTimeout       ← 会话从 09 01 起活了 39.3 秒
```

**"9.2 秒会话预算"不存在。** 会话能活 39 秒，失败是耳机在擦写阶段自己重启。

### 1.3 4.5 秒：数据收完，擦写卡死

无试听、无丢包干扰下：

```
22:40:32.462  UPLOAD_RECEIVED_ALL bytes=150388 elapsed=6572ms
22:40:33.414  UPLOAD_WRITE 158580/300776
（31 秒无进度）
22:41:05.084  flushTimeout
```

`09 05` 的 tag1 = 2 × 包长：第一阶段（接收）写 0→150388，第二阶段（校验写）150388→300776。卡在 53%。

### 1.4 包长与结果

| 包长 | 数据段 | 第二阶段 | 结果 |
|--:|--:|:--|:--|
| 83KB（2.5s） | 4.2s | 走完 | 成功 |
| 106KB（3.2s） | 5.3s | 走完 | 成功（压线） |
| 150KB（4.5s） | 6.57s | 卡在 53% | 失败 |
| 190KB（5.7s） | 8.37s | 未走完 | 失败 |

**天花板在 106~150KB 之间。** 与早期“3.2 秒稳、3.6 秒看运气、4 秒必挂”完全吻合。

---

## 二、根因：480 字节 × 20ms

`7680B` 一窗、`330ms` → 每 **480 字节一个 ACL 包、每包 20ms**。

- 鸿蒙：480B / 20ms = **23KB/s**
- Windows：1013B / 4.8ms ≈ **100KB/s**

差距 4 倍，和最初测到的“慢 4~5 倍”对上。`applyChunkSizeHint` 把写入 chunk 提到 992 无效——协议栈仍按 480 切。

**应用层没有修改 L2CAP MTU / 连接间隔的接口。**

---

## 三、为什么 Windows 能过 5.7 秒

| | Windows | 鸿蒙 |
|:--|--:|--:|
| 数据段 | 3.75s | 8.37s |
| 第一阶段写入时长 | 3.75s | 8.37s |
| 第二阶段 | 4.55s，正常 | 卡死 |

**关键不是总时长，是第一阶段写了多久。** 鸿蒙接收慢一倍，耳机持续写 flash 的时间翻倍，写放大/GC 让第二阶段撑不住。

所以解决方向只有一个：**把数据段压到 4 秒以内**，而不是继续等。

## 四、试过并否决的方向（全部有真机数据）

| 方向 | 做法 | 结果 | 结论 |
|:--|:--|:--|:--|
| 盲发 / 预写 | 回执前连发 2~9 窗 | `ackLag` 从 330ms 涨到 240~1067ms，5.2s 就停止回执 | **有害**，已关闭 |
| 分包协商 | `09 02` 带 tag3 请求 4096 | 耳机仍回 969 | 不接受协商 |
| 分包放大 | 发送侧按 2/4 倍切 chunk | 回执 offset 不按倍数推进 | 耳机按 960 固定切窗 |
| 断点续传 | 传 7680 后断开重连 | `offset = -1`（未收到 09 03），实验无效；未重跑 | 待定，但收益存疑 |
| BLE GATT | 扫描 + `createGattClientDevice` + connect | 扫描到耳机，GATT `Operation failed` | 固件不开放可连接 GATT |
| L2CAP 直连 | `SPP_L2CAP` + psm 3，14 次尝试 | 全部 `2900099` | 系统/耳机不接受按 PSM 硬连 |
| 关 Wi-Fi | 2.4G 共存排查 | 无变化 | 与共存无关 |

## 五、产品结论

### 5.1 上限

- **2.5 秒（83500 字节）：稳定**，维持现状；
- **3.2 秒（106968 字节）：压线**，能过但不建议作为默认值（余量太小，耳机状态差时会挂）；
- **4 秒以上：不可行**，即使数据能传完，擦写阶段也会被耳机自己中断。

### 5.2 如果一定要 5.7 秒

只剩三类方案，都不在应用层：

1. **换传输通道**：BLE 透传（固件未开放 GATT）、或厂商私有协议；
2. **等固件修复擦写**：向华为反馈「自定义音效 >106KB 时第二阶段校验写卡死」；
3. **不做写入**：开盒提示音改为手机端实时播放，绕开整条链路。

### 5.3 界面文案

`toneErr.flushAborted` 里的“长音效的稳定上限约 2 秒”应改为 **2.5 秒**，与实际限制一致。
