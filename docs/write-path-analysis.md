# 盒音写入链路分析：Windows 版怎么做，鸿蒙版能怎么做

> 对象：华为 FreeClip 2（固件自报型号 `BTFT0027`），协议 2（`0x09` 命令族）
> 分析依据：`OpenFreebuds-portable.exe` 反编译（PyInstaller + Python 3.14 + PySide6）
> 与多轮真机日志（2026-11-18）

---

## 0. 一句话结论

Windows 版**没有超过 5.7 秒的魔法**：它的 5.7 秒是 `192000 ÷ 33400` 算出来的一个常量，
不是在这副耳机上验证过的结果。它比我们快的只有**建链**（直连 RFCOMM 通道 1、会话常驻），
而长音效写不进去的原因不在建链，在**耳机擦写阶段对包长的实际上限**——
这一点两边的代码差别改变不了。

---

## 1. Windows 版（OpenFreebuds）拆解

### 1.1 连接层：绕过 SDP，直连通道 1

```python
# openfreebuds/driver/generic/spp_transport.py
sock = socket.socket(socket.AF_BLUETOOTH, socket.SOCK_STREAM, socket.BTPROTO_RFCOMM)
sock.connect((address, channel))
```

- `openfreebuds/driver/huawei/driver/per_model/free_clip_2.py` 里写死 `_spp_service_port = 1`
- **不做 SDP 查询**，直接对 RFCOMM 通道 1 发起连接
- 全项目 197 个模块里没有任何 A2DP/HFP 断开逻辑；相反，它的 `bt_connect` 会用
  `btcom -r -s111e -s110b -c` **主动挂上 AudioSink / HFP**
- driver 对象在应用生命周期内常驻，SPP 会话一直开着，写入时 0 建链

> 这三条加起来，就是"点一下立刻开始写"的全部原因。它跟写入速度、包长都没有关系。

### 1.2 音效来源：华为云端的官方包

```
CLOUD_BASE = https://smarthome-drcn.dbankcdn.cn/device/guide/AAM001
           + /00000A/00000A_promptToneConfig.zip    # 842 B，id + 中英文名
           + /00000A/00000A_promptTone.zip          # 765 KB，18 条 PCM
```

界面里"内置提示音"下拉框的名字来自这个 zip，不是反编译写死的表。
另外有一条云端专属的 200 号「肖邦」（`support=00016D_19`，仅特定机型+固件）。

### 1.3 规格常量

| 常量 | 值 | 含义 |
|:--|:--|:--|
| `TONE_SAMPLE_RATE` | 16755 | 播放采样率（决定音高） |
| `TONE_PACKAGE_RATE` | 16000 | 写入时的换算基准 |
| `TONE_MAX_SAMPLES` | 96000 | 采样点数上限（16000 × 6） |
| `TONE_MAX_BYTES` | 192000 | = 96000 × 2 字节 |
| `TONE_MAX_DURATION` | ≈ 5.73 s | = 96000 ÷ 16755 |
| `TONE_PEAK` | 26213 | 归一化峰值 |

`5.7 秒` 就是从这行除法来的。全项目**没有按机型区分的音效上限**，
`per_model/free_clip_2` 里只有 SPP 端口、降噪模式这些。

### 1.4 上传流程（proto2）

```
1) 2BB4 读 feature16          最多 3 次，间隔 0.5s，每次等 3.0s
2) sleep(PROTO2_PRE_DELAY)    发送前的固定间隔
3) 09 01 + size(>I) + 0a0100  文件信息；等 09 01 应答，读 tag127 credit
                              credit != PROTO2_CREDIT_OK → ToneUploadNotReady
4) 09 02                      会话参数；等 09 02，从 tag3 读分包大小
5) 09 09 01 01 01             开始推流；等 09 03
6) 循环：每窗 8 帧（range(8)），逐帧发 09 04 ...
        再 _wait_window_ack(min(total, offset + 已发*帧长))
        ack 判据：09 03 的 tag1（已收字节）>= expect
        未确认 → 直接抛错，不重传
7) _wait_complete()           见 1.5
8) 写 toneId（2BB4）+ 回读校验
```

### 1.5 擦写判定：它**不等 100%**

`_wait_complete` 的字节码逻辑（变量对应关系已用 `co_varnames` 核对）：

| 收到 | 动作 |
|:--|:--|
| `09 06`（完成） | 记 `complete_seen = True`；若已"落盘"立刻返回 `done`，否则打印"09 06 早到，继续等落盘进度追平" |
| `09 05`（进度） | `cur = tag1`、`total = tag2`；`cur >= total` 时记 `flushed_at`，并把截止时间**收紧到 min(deadline, now + 3s)** |
| 0.1~3s 没有新包 | 有 `flushed_at` → 返回 `flushed`（**当作成功**），否则 `timeout` |

上层拿到 `done` 或 `flushed` 都直接往下写 toneId，**从不要求擦写进度走到 100%**。

> ⚠️ 注意：按实测数据 tag1 恒等于包长的两倍、tag2 是已写量，
> 那么 `cur >= total` 从第一帧起就成立——它的"等落盘"实际退化成
> "再等最多 3 秒没有新包就算完"。无论按哪种解释，**都没有 100% 这道门槛**。

### 1.6 写 toneId

`bytearray(读到的 12 字节)`，只改 `[9:11] = toneId`、`[11] = (id != 0)`，
设备号 / 音量 / 总开关原样保留。注释明确：FreeClip 2 不总 ACK，超时就别报错，以回读为准。

## 2. 我们的实现（鸿蒙）与差异

| 环节 | Windows 版 | 鸿蒙版（当前） |
|:--|:--|:--|
| 建链 | RFCOMM 通道 1 直连，无 SDP | `socket.sppConnect(uuid, secure)`，走 SDP；必须先把 A2DP 断掉 |
| 建链耗时 | ≈ 0（会话常驻） | 0.3~3s（受 ACL 收敛影响） |
| 会话 | 常驻 | 写完必断（耳机自己收），90s 池只对不写闪存的操作有效 |
| **写 toneId 的时机** | `id=0` → 检查双耳在盒 → **写目标 id（43）→ 传包 → 不再改动** | `id=0` → 传包 → **传完再写 43 并选中** |
| 上传协议 | `09 01` → `09 02` → `09 09` → 8 帧/窗 | 同左 |
| 擦写判定 | `flushed` 即可，最多再等 3s | 要求 `tag2 == tag1`（= 2×包长），上限 60s |
| 规格上限 | 192000 B / 5.73 s | `MAX_BYTES = 192000`、`MAX_SECONDS = 5.7` |

两处实质差异：

1. **擦写判定**——它没有 100% 门槛，我们有（已在本轮改为"音频回连即认为处理完，重连补选"）。
2. **选中的时机**——它先选中目标槽位再传数据，传完不再动；我们反过来。

第 2 点值得单独测一次：如果耳机是按"当前选中槽位"决定擦写缓冲区大小的，
那么先选中 43 再传包，行为可能完全不同。

## 3. 3.5 秒为什么写不进去

### 3.1 实测数据

| 音效 | 包长 | 擦写总量（tag1） | 结果 |
|:--|--:|--:|:--|
| 0.8 s | 27 920 | 56 016 | 完成 100% |
| 2.0 s | 66 888 | 133 776 | 完成 100% |
| 3.2 s | 106 968 | 213 936 | **完成 100%** |
| 3.5 s | 116 988 | 233 976 | 停在 ~96.8%，随后耳机重启音频，槽位失效→回落默认音 |
| 3.8 s | 127 008 | 254 016 | 停在 245 792 / 254 016（96.8%） |

### 3.2 证据链

```
16:53:14.588  UPLOAD_RECEIVED_ALL bytes=106968      ← 数据全部送达
16:53:17.952  UPLOAD_WRITE 213936/213936 → DONE      ← 3.2s 擦写走满
...
15:53:23.4    （3.8s）最后一帧 245792/254016
15:53:23.5    A2DP state=0 → 25.9 state=1 → 37.3 state=2
              ← 耳机放弃本轮擦写并重启音频，此后一个字节都不再回报
```

- 数据阶段从来没问题：`09 01` 报多少就收多少，耳机全部接下
- 失败的都在**擦写阶段**，且总是差最后几个百分点
- 失败后开盖听是**默认音**，说明自定义槽被置为无效（不是"旧音效还在"）

### 3.3 结论：这是耳机侧的包长上限，不是协议或代码问题

3.2 s 能走满 100%、3.5 s 不能，两者走的是同一段代码、同一个窗口参数、同一个分包大小。
中间没有分支能造成这种差异。

按 33400 B/s 换算，边界落在 **106 968 ~ 116 988 字节**之间，
也就是 **3.20 s ~ 3.50 s**。

> 由此推论：即使 Windows 版把 `192000` 填进去，这副耳机也会在同一个位置失败。
> 它的 5.7 秒是理论值，不是 FreeClip 2 的实测值。

## 4. 鸿蒙侧能不能"像它那样"？

### 4.1 官方 API 能力核对（本地 SDK `@ohos.bluetooth.socket.d.ts`）

```ts
interface SppOptions {
  uuid: string;        // SDP 记录里的 UUID
  secure: boolean;     // 加密通道
  type: SppType;       // SPP_RFCOMM=0 / SPP_L2CAP=1 / SPP_L2CAP_BLE=2（后两个 API 20+）
  psm?: number;        // API 20+，仅 L2CAP 使用
}
function sppConnect(deviceId: string, options: SppOptions, callback: AsyncCallback<number>): void;
```

**没有 `channel` / `port` 参数**，也没有"按通道号连接"或"读对端 SDP 记录"的接口。
也就是说：**鸿蒙不允许像 Windows 那样跳过 SDP 直连 RFCOMM 通道 1**。

唯一理论上等价的路子：
`type = SPP_L2CAP` + `psm = 3` → 拿到原始 L2CAP 通道 → **自己实现 RFCOMM 帧**
（SABM/UA 建链、UIH 带地址字段 channel=1、FCS 校验）。

- 收益：省掉 SDP，建链接近 0
- 成本：RFCOMM 状态机 + 重传 + 流控，全部自己写；还要赌系统允不允许对端未声明 PSM 的连接
- **风险远大于收益**：建链只占 1~3 秒，且失败时可以靠重试掩盖

### 4.2 长音效这个问题的真正解法只有三条

| 方案 | 做法 | 预期 |
|:--|:--|:--|
| **A. 按实测定上限** | 二分找边界，把 `MAX_SECONDS` 设到边界下方 | 确定能成功，代价是上限可能只有 ~3.4 s |
| B. 擦写不依赖 100% | 音频回连即认为已处理完，重连补选（已实现） | 只改善"等 60 秒才报错"，救不了包长超限 |
| C. 对齐它的上传流程 | 去掉上传中途那条 `2BB4`（参考实现全程不发） | 低成本，值得一试，但大概率不是主因 |
| D. L2CAP + 自写 RFCOMM | 见 4.1 | 只优化建链，与本问题无关 |

## 5. 建议的下一步（按顺序）

### 5.1 先做：二分出真实上限（一次 3 条就能定）

用同一段音频裁成 **3.3 s / 3.4 s / 3.45 s**，各写一次，看日志：

- 出现 `UPLOAD_WRITE …/… → UPLOAD_DONE` = 成功
- 停在 9x% 后静默 = 失败

三种结果对应三种结论：

| 结果 | 结论 |
|:--|:--|
| 3.4 成功、3.45 失败 | 边界 ≈ 114 688 B（224 KiB ÷ 2），上限设 **3.4 s** |
| 3.3 成功、3.4 失败 | 边界 ≈ 110 000 B，上限设 **3.3 s** |
| 三条全失败 | 3.2 s 已经是天花板（可能是那次运气好），上限设 **3.2 s** 并复测一次 |

### 5.2 再做：把上限和文案对齐

- `ToneSpec.MAX_SECONDS` / `MAX_BYTES` 按实测值收紧
- 转换时超过上限直接裁掉并提示"该耳机单条上限约 X 秒"，不再让用户白等一次失败
- README 和「更新日志」同步说明：5.7 s 是协议理论值，本机型实测为 X

### 5.3 可选：验证顺序差异

参考实现先写目标 toneId 再传包，传完不再改动。若 5.1 的结论是"确有硬边界"，
这个顺序改变不了边界；若 5.1 出现"3.4 能过、3.5 不过但 3.45 又能过"这种不稳定结果，
那就值得把顺序调成和它一致再测一轮。

改动点很小：`upload()` 里把 `setTone(0, false, vol)` 换成 `setTone(customId, true, vol)`，
并去掉上传后那次 `confirmTone`（保留回读校验）。

### 5.4 不建议：现在动 L2CAP

建链 1~3 秒的收益，换一个要自己实现 RFCOMM 的高风险模块，不划算。
如果将来真的要压这 1~3 秒，更稳的方向是"写完不要立即断会话、
在耳机休眠前提前重建"——但前提是耳机愿意在我们不释放 A2DP 的情况下开 SPP，
而这一点已经被前面几轮日志否定了。

## 6. 附：可复用的命令字节

```
读 feature16     2B B4 01 01 10
文件信息         09 01 01 01 01 02 02 00 00 03 01 00 06 01 04 09 04 <size:4B BE> 0A 01 00
会话参数         09 02
开始推流         09 09 01 01 01
数据帧           09 04 FF <offset:4B BE> <seq:1B> <chunk>
写 toneId        2B B4 01 01 10 02 0C 01 01 <vol> 00 00 00 00 00 00 <id:2B BE> <sel:1B>
```

- `chunk` 用耳机在 `09 02` 里给的大小（FreeClip 2 给 960）
- 每窗 8 帧，等 `09 03` 的 tag1 ≥ 已发字节再发下一窗
- 数据帧总数上限：`ceil(size / chunk)`
