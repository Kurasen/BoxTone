# 写入引擎（refactor/write-engine）

> 取代 `services/bluetooth/ToneClient.ets`（1947 行）与 `CaseWriteService` 里的编排逻辑。
> 协议字节、建链时序、各项超时**全部沿用旧实现**——那些数值来自多轮真机日志（见
> `write-path-analysis.md`、`write-duration-gap.md`），这次重构不动它们，只动结构和系统层保护。

---

## 1. 为什么要重构

旧实现「写不进去」的问题，按来源分三类：

| 来源 | 旧实现的表现 | 根因 |
|:--|:--|:--|
| 鸿蒙进程调度 | 写到一半断开、切出去看一眼消息就失败 | 应用退到后台后很快被挂起，JS 线程停下，耳机等不到下一窗就收掉串口。旧版只在页面里开了屏幕常亮，挡不住切后台和按电源键 |
| 并发交错 | 偶发坏帧、回执错配、回滚和新写入抢串口 | 保活定时器、命令、数据窗口各自调 `sppWriteAsync`，一条多次写入的帧中间可能被插进别的帧；写入、回滚、音频恢复各用定时器触发，只靠两个布尔量互相避让 |
| 状态分散 | 难以判断「这次失败后该干什么」 | 冷却、沉降、协议缓存、断音频是否成功过……十来个静态字段散落在 ToneClient 与 CaseWriteService 里，读写点遍布建链、上传、保活、收尾 |

写入时长上限（2.8 秒）**不是**这次能改的：瓶颈是系统 SPP 的 480B/20ms 分段和耳机擦写第二阶段，
详见 `write-duration-gap.md`。重构后的引擎让那条结论更容易复测（上传状态机可单测、日志按阶段分段）。

## 2. 结构

```
services/
├── CaseWriteService.ets      门面：前置检查、读文件、把结果翻译成 WriteResult（页面接口不变）
└── write/
    ├── WriteEngine.ets       编排：串行队列、热会话池、整包重来 / 只补选中 / 失败回滚、音频恢复
    ├── WriteTask.ets         写入任务的全局状态：页面确认后交给它，写入弹窗只读它
    ├── WriteGuard.ets        系统保护：蓝牙长时任务 + 短时任务 + 屏幕常亮（引用计数）
    ├── LinkConnector.ets     建链策略：冷却 → 沉降 → 松开音频 → 双通道交替 → 判半死通道
    ├── AudioLink.ets         A2DP 状态、断开（含认领）、擦写期间压制回连
    ├── SppChannel.ets        串口：收包拆帧、写入串行化、判死即唤醒
    ├── PacketInbox.ets       回包收件箱：事件驱动，替代 sleep 轮询
    ├── MbbSession.ets        命令层：查询/选中/型号/协议探测/保活，实现 UploadPort
    ├── ToneUploader.ets      上传状态机：只依赖 UploadPort，可脱离真机单测
    ├── DeviceTimeline.ets    每台耳机的时间线：冷却、沉降、协议缓存……收拢在一处
    ├── SppErrors.ets         系统错误码 → 面向用户的 ToneError
    ├── WriteTypes.ets        阶段、端口接口、上传报告、结果
    └── WriteSpec.ets         引擎新增的参数
```

依赖方向只有一个：`CaseWriteService → WriteEngine → (LinkConnector, MbbSession, ToneUploader) → SppChannel → PacketInbox`。
`ToneUploader` 不碰任何系统 Kit，`entry/src/test/WriteEngine.test.ets` 用一台「假耳机」跑完整流程。

## 3. 一次写入

```
WriteGuard.acquire()                      短时任务 + 常亮
└─ 串行队列（同一时刻只有一个设备操作）
   └─ 第 1 轮
      ├─ 等设备就绪（冷却 / 沉降，界面显示剩余秒数）
      ├─ 建链（热会话可复用则探活后复用）
      ├─ 握手：读状态 → 读型号 → 探测协议
      ├─ 松开音频（传输前又被系统连回时）
      ├─ ToneUploader：声明 → 选中目标槽位 → 分窗传输 → 擦写 → 确认
      └─ 收尾：未预选则补发选中
WriteGuard.release()
```

### 失败处置：按「数据走到了哪一步」决定

| 失败时的状态 | 处置 | 理由 |
|:--|:--|:--|
| 数据还没收完就断链 / 回执超时 | 整包重来第 2 轮 | 耳机侧没有落盘 |
| 数据收完，只差选中（`DATA_WRITTEN`） | 换一条新链路只补一条选中命令 | 不必重传 80KB |
| 已预选槽位，数据没写完（含擦写卡死） | 返回失败，后台**回滚到写入前在用的音效** | 槽位是空的，开盖会没声音；旧版一律回落出厂音，新版之前是内置音就切回那条内置音 |
| 格式被拒 / 机型不支持 | 直接失败，不重试 | 重试也不会好 |

回滚、恢复默认、切换内置音、音频恢复都排进同一条串行队列，不会和新的写入交错。

## 4. 鸿蒙相关的设计取舍

| 问题 | 方案 | 接口（本地 SDK 核对） |
|:--|:--|:--|
| 退后台被挂起 | 短时任务 | `backgroundTaskManager.requestSuspendDelay`（API 9，无需权限；同一时刻最多 3 个，用完 `cancelSuspendDelay`） |
| 自动熄屏 | 屏幕常亮 | `window.Window.setWindowKeepScreenOn` |
| 为什么不用长时任务 | — | `startBackgroundRunning` 需要 `KEEP_BACKGROUND_RUNNING` 权限、`backgroundModes` 声明与常驻通知，上架要单独说明；一次写入最多几十秒，短时任务足够 |
| sppRead / 写完成都在主线程 | 进度限频 120ms | 擦写进度约 80ms 一包，全推给界面会让主线程忙于重绘 |
| 写入交错 | `SppChannel` 内部写队列 | 一个 payload 的所有分片写完才轮到下一个；保活与传输由「静默」开关互斥 |

`EntryAbility` 只做登记：`onCreate` 里 `WriteGuard.attach(context)`，`onForeground/onBackground` 里报告前后台。
写入期间进过后台会记进 `DEVICE_MATRIX ... bg=true`，方便和断链日志对照。

## 7. 2026-11-26 19:05 真机：连续写入后串口卡死

现象：连写 3 条都成功（中途都切过后台，`bg=true result=ok`，短时任务生效）；
第 4 条在上一条写完 13.8 秒后开始，之后 3 分钟内的 4 轮写入全部失败。

时间线：

```
19:05:05.099  UPLOAD_FLUSH_100            第 3 条擦写走满（未补 09 06）
19:05:08.140  UPLOAD_DONE confirm=silent
19:05:11.370  A2DP state=2                耳机自己把音频连回来
19:05:21.993  FLASH_SETTLE_SKIP           沉降期因「音频已恢复」提前 1.2 秒放行
19:05:23.181  CONNECT secure=false        3 秒无任何回应（超时）
之后          -1 / 10ms 内的 2900099 交替  合计 4 轮、约 60 次尝试，全部被拒
```

判断：耳机还在收尾时被发起连接，串口进入卡死状态；这与旧实现
`FLASH_SETTLE_MIN_MS` 注释里 11-26 12:30 那次是同一个问题（当时 6 秒就放行）。
重构沿用了旧时序，所以没有修掉它。

改动：

| 项 | 旧 | 新 |
|:--|:--|:--|
| 写完后的最小间隔 | 15 秒，音频连回且满 10 秒可提前放行 | `POST_FLASH_GAP_MS` = 25 秒，不提前放行；界面逐秒倒计时 |
| 卡死识别 | 无，耗满 15 秒预算，提示「被其他应用占用」 | 连续 4 次 150ms 内的 2900099，或出现过「音频已松开仍无回应」后预算耗尽/音频回连 → 立即失败，提示合盖 10 秒重开 |

25 秒是按现有样本（6 秒卡、11 秒好、13.8 秒卡、27 秒好、52 秒好）取的保守值，需要更多数据再收紧。

### 7.1 补充（19:14）：合盖也恢复不了

用户确认失败后合过盖。日志里能看到的断开：19:06:55→57、19:08:11→13（各约 2 秒），
19:07:20→39（约 19 秒，期间耳机切到星闪又切回）。19:07:20 那次断了 19 秒，之后照样全部被拒；
19:08:18 那轮更是 12 次全部在 15ms 内回 2900099——请求根本没出手机。

所以卡住的更可能是**手机这边**（协议栈或本进程的串口状态），不是耳机：合盖只能重置耳机。
可疑起点是 19:05:23 那次 3 秒无回调的 sppConnect：系统里可能一直挂着这条出站请求，鸿蒙没有接口能取消它。

已加的诊断（release 包也记，不含地址）：

| 日志 | 含义 |
|:--|:--|
| `CONNECT_HUNG ... open=[] pending=N` | sppConnect 超时无回调；pending 为还没回来的请求数 |
| `CONNECT_LATE ok= id=` | 超时后才回来的连接，成功会立刻关掉 |
| `SOCKET_LEDGER before_connect open=[...]` | 每次建链前本进程还没关的串口；非空即漏关 |
| `SOCKET_SWEEP` | 建链前关掉遗留串口 |

卡死提示改为先「关开手机蓝牙」，再「划掉应用重开」。待用户实测哪一步能恢复，再定自动处置。

### 7.2 结论（19:17）：卡在本进程，重启应用即恢复

用户实测：卡死后**划掉应用重开就恢复**，不用关开蓝牙。说明卡住的是本进程在系统蓝牙服务里登记的串口状态
（最可能是 19:05:23 那条 3 秒无回调的 sppConnect），进程退出时系统才回收。合盖只重置耳机，所以无效。

处置：

| 项 | 做法 |
|:--|:--|
| 判定 | 单轮内满足卡死条件即判定（见 7 节）；判定过一次就在进程内记住，之后建链失败一律按卡死归因，成功则清除（`LINK_UNWEDGED`） |
| 归因 | `ToneErrorReason.WEDGED` → `WriteReason.WEDGED`，错误码 `3005`，不自动重试、不整包重来 |
| 恢复 | 失败弹窗给「重启应用」按钮，调用 `ApplicationContext.restartApp`（API 12 起，须主线程、前台；不走 onDestroy，先落盘日志）。只由用户点按触发，不自动重启 |
| 预防 | 写完一条后等满 `POST_FLASH_GAP_MS`（25 秒）再建链，不再被「音频连回」提前放行 |

注意：用户反馈「重开后第二次写入有时失败」时测的是**旧时序**（15 秒、可提前放行），与 7 节的触发条件一致，需在新版本上复测。

## 8. 2026-11-26 19:28~19:37 真机：后台超过约 5 秒 → 下一次写入秒拒

| 写入 | 期间在后台 | 本次 | 下一次 |
|:--|--:|:--|:--|
| 19:03:07 | 1.6 s | 成功 | 成功 |
| 19:03:48 | 4.2 s | 成功 | 成功 |
| 19:04:54 | 8.8 s | 成功 | **卡死**（当时归因为沉降提前放行，现在看是同一个问题） |
| 19:28:23 | 5.8 s | 成功 | **卡死** |
| 19:29:51 | 5.3 s | 成功 | **卡死** |
| 19:32:30（熄屏） | 7.9 s | 成功 | **卡死** |
| 19:34:22 | 6.2 s | 成功 | **卡死** |
| 其余 11 次 | 0 | 成功 | 成功 |

卡死的形态完全一致：下一次第一枪 sppConnect 10ms 内回 2900099，`SOCKET_LEDGER open=[] pending=0`（我们没有漏关串口），
只有重启应用进程能恢复。

判断：短时任务只保证进程不被挂起；后台超过约 5 秒后，系统对本应用的蓝牙资源做了管控，
已建立的串口不受影响（本次写入照样成功），但之后的新连接被本机协议栈直接拒绝，且回到前台也不解除。

处置：写入期间申请 `BackgroundMode.BLUETOOTH_INTERACTION` 长时任务（需 `KEEP_BACKGROUND_RUNNING` + `backgroundModes: ["bluetoothInteraction"]`，
写入时会出现一条系统通知），短时任务保留为兜底。`DEVICE_MATRIX` 新增 `bgMs=` 与 `bgTask=bt/transient`，用于验证。

**这是假设**：要靠复测确认——长时任务生效（`bgTask=bt`）时后台 8 秒，下一次写入应正常。

### 8.1 场景 4（中途合盖）

- 19:37:16 合盖后耳机回 `109017`（22:55:37 第二例证实为传输中合盖，见 14 节），失败后会话被放回了热会话池；
  3 秒后回滚复用了这条死会话（`2901054`），随后盒盖合着时的建链全部被秒拒，又被判成了进程卡死。
- 19:37:44 开盖后的写入是**慢速 -1**（约 600ms，请求到了耳机、被耳机拒），属于刚开盖未就绪，却因「进程内判定过卡死」被归成卡死。

修正：失败过的会话一律关闭、不进热会话池；回滚前先看音频是否连着（盒盖开着），没连就只检查不建链，最多约 1 分钟；
进程级卡死只在本轮仍有「秒拒」时才沿用，慢速 -1 按耳机未就绪处理。

### 8.2 复测（19:46~19:50）：长时任务生效，秒拒消失；出现新的失败形态

- 6 次写入全部 `bgTask=bt`；19:49:48 那次在后台 8.2 秒（`bgMs=8168`）仍然成功。
- 下一次（19:50:29）**不再是 10ms 的 2900099**，而是 11 次约 500ms 的 `-1`：请求到了耳机、被耳机拒。
  说明后台导致的本机秒拒已被长时任务解决（假设成立）。

新失败的原因：

```
19:50:01.269  UPLOAD_FLUSH_100
19:50:04.156  A2DP state=2              耳机写完、自己把音频连回来
19:50:04.374  AUDIO_RELINK_SUPPRESS     我们在「等 09 06」的最后一刻把它压了下去
19:50:04.586  A2DP state=0              此后音频再没回来
19:50:15      新写入取消了待执行的音频恢复
19:50:29      AUDIO_LINK_IDLE → 串口连续被耳机拒
```

所有成功的建链都是「音频连着 → 我们断开 → 1 秒后连串口」；音频本来就断开时从未成功过。

修正：
1. 擦写走满 100% 后不再压制音频回连（`UploadPort.idle(suppressAudio)`）。
2. 建链前音频不在：先 `connectAllowedProfiles` 连回来（最多 5 秒），再走正常的断开流程；
   建链中遇到慢速 -1 且音频不在，同样补一次。

### 8.3 对照（19:55，旧包）：同样后台 8 秒，这次下一条成功

| | 19:50（失败） | 19:55（成功） |
|:--|:--|:--|
| 擦写 100% | 19:50:01.269 | 19:55:41.649 |

另：19:55 是冷启动后的第一条写入，快照里 activeName 还是空的，被当成非华为耳机给了中性提示；

### 8.4 复测（20:01，新包）：卡死的真正起点是「挂起的 sppConnect」

```
20:01:14  第 1 条：后台 5.1 秒，bgTask=bt，成功
20:01:34  耳机写完、自己连回音频（100% 后不再压制，8.2 节生效）
20:01:54  第 2 条：音频连着 → 断开 → 1 秒后连串口（标准顺序）
20:01:55  sppConnect secure=false：3 秒无回调 → CONNECT_HUNG pending=1
20:01:58  之后每条请求约 150ms 被拒；挂起的那条到日志结束（20:02:16）都没回来
```

对照第一次卡死（19:05:23）：同样是第一枪 3 秒无回调，之后全部被拒、重启才好。
两次都没有漏关的串口（open=[]），唯一的共同点是那条挂起的请求（pending=1）。

鸿蒙没有接口能撤回一条已发出的 sppConnect；进程退出时系统才会回收，所以重启应用能恢复。

修正：
1. 请求超时后**不再立刻发下一条**，最多再等 10 秒让它迟到回调：迟到成功就直接用这条串口，
   迟到失败照常重试，等满仍没回来才判定卡死（`CONNECT_HUNG_WAIT` / `_ADOPTED` / `_FAILED`）。
   这同时是一次实验：如果卡死是「挂起期间又塞请求」造成的，这样就能避开。
2. 8.2 节加的「建链中补连音频」误触发：音频是我们刚断开的（RELEASED）也被当成了没连，
   白白多走了一轮连回—断开。改为只在音频从没连上过（IDLE）时补。

### 8.5 复测（20:13~20:15，长音效）：挂起已能自愈；后台导致的秒拒仍在

## 9. 建链提速：加密通道优先（2026-11-26 20:35，待验证）

统计当天全部 34 次成功建链（音频断开后 1 秒发第一枪）：

| 形态 | 次数 |
|:--|--:|
| 非加密 -1（0.5~2.1 秒）→ 隔 0.5 秒 → 加密成功 | 28 |
| 其他（含重试、挂起） | 5 |
| 非加密第一枪直接成功 | 1 |

成功那一枪距音频断开多为 2.0~2.5 秒；成功的通道 31 次加密、3 次非加密。
总耗时中位数约 2.9 秒，其中第一枪失败 + 间隔白花 1.1~2.6 秒。

两种解释无法从现有数据区分：
- **通道**：这款耳机非加密第一枪总被拒，加密才行 → 加密优先能省 1~2.5 秒；
- **时序**：断开音频后要 ~2 秒才能接受串口，第二枪成功只因来得晚 → 加密优先会在 1 秒处失败、退回非加密，耗时与现在相当。

两种情况下改成加密优先都不会更慢，所以直接改为**固定加密优先、非加密兜底**。
不记「上次连通的模式」：那 3 次非加密成功都在加密先失败之后，更像时序巧合，记下来会让下一次退回非加密优先。
日志新增每一枪的 `sinceRelease=`、成功时的 `tries=`，用于判断是哪一种。
同时去掉了「加密通道大包可能被中断」的告警（当天 31 次加密写入全部正常）。

### 9.1 结果（20:42~20:44）：是时序，不是通道

加密优先后 4 次建链形态完全一致：断开音频 1.0 秒时加密被拒（-1，约 0.8 秒），2.2~2.4 秒时非加密一次就通，
总耗时 2.8~2.9 秒，与之前相同。对照非加密优先时「1 秒非加密被拒、2 秒多加密成功」，两种通道都能用，
决定成败的是距断开音频的时间：耳机断开音频后约 2 秒才接受串口（当天最早一次成功在 2.04 秒）。

修正：断开音频后等待从 1 秒改为 2 秒（`WriteSpec.RELEASE_TO_CONNECT_MS`），第一枪即可连上，
预计建链从约 2.9 秒降到约 2.4 秒。通道顺序保留加密优先，不再有实际意义。

### 9.2 复测（20:52）：2 秒也不行，9.1 的结论撤回

断开音频后等 2 秒，2 次建链仍是「2.0 秒加密被拒（-1，约 0.7 秒）→ 3.2 秒非加密成功」，总耗时 3.76 秒，比等 1 秒还慢 0.9 秒。

| 第一枪 | 第一枪时刻 | 结果 | 第二枪 |
|:--|:--|:--|:--|
| 非加密 | 1.0 s | 被拒（47 次里 46 次） | 加密成功 |
| 加密 | 1.0 s | 被拒（4/4） | 非加密成功 |
| 加密 | 2.0 s | 被拒（2/2） | 非加密成功 |

结论：**断开音频后的第一次 sppConnect 几乎必被耳机拒绝，与通道、等待时长都无关；第二次才成功。**
更像是第一次请求起了「唤醒/触发」的作用（耳机侧切换 profile 或系统补一次 SDP），日志里看不到更多信息。

处置：等待改回 1 秒（约 2.9 秒）。第二枪之前还有 0.5 秒间隔，理论上最多再省约 0.4 秒，
但需要缩短重试间隔，收益很小，暂不做。

### 13.1 保存窗口与沉降期统一成一个时钟

原来两个时钟：设备页「保存中」是写入成功时标的固定 16 秒（`AUDIO_RESTORE_DELAY_MS`），

所以设备页变回「已连接」后点写入，弹窗仍要再等 4~9 秒。

| 改动 | 说明 |
|:--|:--|
| 写入路径 | 那一轮 finally 里 `endUpload` 记下沉降期后，`markCaseSettling(settleLeft())`。不能放在 try 里：成功路径的 `return` 先于 finally，那时沉降期还没记 |
| 收完整包但失败（擦写超时、只差选中） | 同样进保存窗口：耳机确实在擦写，引擎下一次也要等 |
| `scheduleAudioRestore(deviceId, settleMs)` | 写入 / 只补选中传 0（窗口由上面设置）；命令类与回滚沿用 16 秒 |
| 音频恢复定时器 | 到点不再 `endCaseSettling`：窗口只由 BluetoothService 自己的定时器结束，否则 20~25 秒窗口会在 16 秒被掐掉 |

依赖方向不变：WriteEngine 把剩余毫秒数推给 BluetoothService，BluetoothService 不引用 write/。
效果：设备页「保存中」与弹窗「约 N 秒」结束于同一时刻；设备页一变回已连接，写入不再等待。
设备页本身**不显示秒数**（倒计时只在写入弹窗里）；评估后不加：用户写入时看的是弹窗，不会专门切到设备页看剩余时间。
设置窗口时记 `CASE_SETTLING ms=`，应与下一条写入的 `FLASH_SETTLE wait=` 加上间隔时间吻合。

### 13.2 建链太晚：关掉按标准顺序重建一次（`WriteSpec.STALE_LINK_MS` = 10 秒）

「第一枪挂起 → 迟到失败 → 再试才连上」已有 3 例，连上时距松开音频 14.6~15.7 秒，第 1 轮全部作废：

| | 距松开 | 连上前后 | 结局 |
|:--|--:|:--|:--|
| 21:47:02 | 15.7 s | 握手后 246ms 音频被连回 | 09 09 后无窗口 → 回执超时 |
| 22:35:27 | 14.6 s | 连上前 50ms 音频被连回；`HANDSHAKE_DONE ms=358 audio=linked` | `AUDIO_PRE_SUPPRESS` 断音频 → 第一包 2901054 → 冷却 |
| 22:38:06 | 15.4 s | 连上前 100ms 音频被连回；`HANDSHAKE_DONE ms=357 audio=linked` | 同上；第 2 轮冷却走满、音频没回来 → 连回音频 → 再挂起 → 卡死 |

正常建链 2~3 秒、握手 67~89ms；20:13 那次挂起后 7.7 秒连上的照常成功（8.5 节）。

处置（`WriteEngine.openSession`，写入 / 命令 / 回滚共用）：新建的串口若 `sinceRelease > 10 秒`，记 `LINK_STALE`，
自己关掉（主动关活链路只记 `SOCKET_SETTLE_MS` 收尾间隔，不记冷却、不算一轮），用同一个 LinkConnector 再走一遍
「音频不在就先连回 → 断开 → 1 秒 → 连串口」；只重建一次，第二条再晚也照用。

预期：22:35 那种从约 50 秒降到约 20 秒；22:38 那种第 2 轮不再先吃 13.8 秒冷却。
**挡不住的**：第二次建链同样可能挂起（22:38:27 那条到导出时仍 `pending=1`），挂起本身的原因仍未知，
那时照旧判卡死、给「重启应用 / 重启蓝牙」。

**这是假设**，复测看：`LINK_STALE` 之后第二次 `LINK_OPEN` 的 `sinceRelease` 是否回到 2~3 秒、`HANDSHAKE_DONE audio=down`、本轮是否一次成功。

### 13.3 读代码时发现、未改

- `AUDIO_PRE_SUPPRESS`（握手后音频被连回就断开）：现有两例都紧跟 2901054，但两例都是建链太晚的链路，13.2 之后不会再走到；正常时序下是否也会带走串口没有样本，先不动。
- `applyOnly`（数据已写入、只差选中）在外层那一轮 finally 之前执行，所以它建链时沉降期还没记，只受掉线冷却约束。走到它要求预选失败，今天所有写入都是 `TONE_ALREADY_SELECTED`，暂不动。

23:20:00  开盖后直接写入成功，LINK_UNWEDGED —— 根本没卡死，是盒盖合着

`LinkConnector.open` 在建链前（`before_connect`）或慢速拒绝后补连（`after_reject`）遇到 **TIMEOUT** 就抛

窗口外音频没连时，引擎本来就先连回音频，连不上 5 秒内就失败，和点击时拦截只差这几秒，却不会误拦「手动断开音频后再写」的情况。
